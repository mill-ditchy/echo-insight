# 抓取与后台任务实施记录及后续建议

增量抓取、持久分析队列和 SQLite 历史已接入生产路径。首次启动会校验并导入旧历史，保留原 JSON 和迁移备份；定时检查发现新内容后保存记录并提交任务，独立工作进程执行分析。下文记录实现范围、升级操作以及后续进一步优化的设计。

当前公开源码以 Windows 端为准，伴侣源码、手机服务和专用测试尚未进入公开仓库，计划后续单独更新；公共网页和宿主能力接口继续保留。默认发布与回归不需要安卓工具或原生资源；源码可用不代表正式 Release 已发布。

## 当前实现

- 历史与任务使用 `data/update_history.sqlite3`，保留阅读状态、成功简报与未完成记录，取消 1000 条保存截断。历史通过分页接口按批次显示，来源统计包含完整历史。
- 各分析入口共用持久队列。同一内容只保留一个活跃任务，工作进程拥有租期、心跳和领取代次，失效 owner 不能提交进度、结果缓存或完成事务。
- 成功结果与任务完成在一个 SQLite 事务中发布；临时失败进入延迟重试，达到上限保留失败记录。各来源轮转，CPU 和模型分析以单执行器运行。
- AI请求与处理阶段共用结构化错误类别及响应完整性检查。余额、凭证、证书校验和模型配置错误不自动重试；临时请求沿用已有次数上限，分段与角色识别的429不立即重试。缺少结束标记的兼容网关仍可使用，声明截断的正文或JSON不会作为新结果保存。
- 每次分析尝试开始时捕获AI接入与视频设置，显式传给抽帧、片段理解和摘要。任务 `version` 仍为入队去重指纹；任务payload另存最新执行尝试的公开配置、配置哈希及领取代次，不保存密钥或凭证引用。成功历史保存对应配置，重分析失败保留旧结果的配置；重试开始时可采用新设置。旧任务无需迁移。
- 内容状态经历史模块集中处理，队列不再访问历史私有锁；SQLite只修改涉及的内容，领取、进度、取消、失效恢复和成功发布共享旧成功结果保护规则。任务完成与结果仍在同一事务中提交；生产启动明确选择SQLite，旧测试/工具路径的自动后端判断作为兼容行为保留。
- 平台统一实现 `scan(uid, FetchContext) -> FetchResult`。游标、关注边界与平台检查点由适配器解释；当前已收录ID与补抓冻结锚点分开，部分范围及未读完的详情队列不报完整。旧平台 `fetch/fetch_incremental` 入口保留兼容。
- 历史与来源GET只查询，不恢复缓存、采集或唤醒worker。启动、定时检查和手动重试显式恢复缓存；来源首次打开需要补建时，网页调用POST准备命令。启动会恢复遗留的中断重分析，纯查询不会反复启动进程。
- 来源与首页的分页/轮询按内容键合并，刷新保留已加载集合并请求相应范围；简报按平台及内容键查询。offset分页仍不能提供跨请求数据库快照。
- 共享字幕格式、视频/笔记分析、官方媒体下载和 Edge 上下文位于中性模块，保留原缓存目录、键与平台网络边界。公开网页保留 `CyberHost` 宿主能力接口及 `CyberApp.back` 返回处理；本机伴侣试作的传输与构建验证属于未公开范围，不代表安卓已随仓库发布。
- “设置 → 后台任务”显示等待、运行、重试和失败状态，可以取消等待任务并设置每日分析尝试上限。0 表示不限，重试计入上限；单次分析可能包含多次模型请求，次数预算不等于金额预算。
- B站动态和投稿列表、知乎活动接口按页检查，每轮最多 5 页；达到预算保留后续位置。补抓期间冻结旧锚点，每次先检查首页，发现内容与位置一起持久化，入库后再确认收录。
- RSS/RSSHub 检查当前 Feed 的全部条目，支持 GUID 身份、旧链接身份兼容和 ETag/Last-Modified/304；首次展示仍为 3 条，首次 Feed 身份完整收录到去重关联中。
- 抖音有可信首次时间边界时检查同批缺口，排除关注前历史；旧来源没有边界时保留原保守规则。小红书保持已有增量发现队列与读取上限。
- “查看可清理媒体”先显示超过 30 天的原始媒体数量，再由用户执行清理。活跃工作进程或未完成任务存在时拒绝清理，成功简报、证据和人物资料不参与清理。

配置与凭证仍使用原有 JSON/加密文件，抓取确认状态同时保存在数据库中。SQLite 的内容写入、状态/阅读修改和任务发布已按涉及条目更新；JSON 回退仍保留完整快照，导出及页面聚合可以读取全量历史。接口分页继续使用 offset；下面提出的全部字段独立建表、稳定游标分页、按内容指纹自动更新摘要和所有请求层共用费用预算尚未实现。真实平台可能变更接口，浏览器回退会明确提示范围有限。

## 升级 备份与回退

先退出旧版应用，等待正在运行的旧检查结束，再启动新版本。主窗口关闭后新版本分析任务仍会由独立进程处理，可在后台任务中查看。不要让旧版 JSON 写入进程与新版本同时运行。

手动迁移与备份命令如下，执行维护命令前应关闭应用并等待后台任务结束：

```powershell
.\.venv\Scripts\python.exe scripts/history_storage.py migrate
.\.venv\Scripts\python.exe scripts/history_storage.py backup --output output/history-backup.sqlite3
.\.venv\Scripts\python.exe scripts/history_storage.py export --output output/history-export.json
```

首次导入保留 `data/update_history.json`，另存 `data/update_history.migration-backup.json`，记录原内容 SHA256 和导入数量。校验失败不写完成标记，不覆盖原 JSON；修复后可重复迁移。活动数据库备份通过 SQLite backup API 包含已提交的 WAL 内容。

回退前导出最新历史与阅读状态，再恢复旧版本代码，将导出的 JSON 复制为旧版本的 `data/update_history.json`。保留数据库和完整导出副本；旧版本仍可能重新启用 1000 条截断，不能把唯一完整副本交给旧程序继续写入。来源配置和凭证文件沿用现有位置。

## 已完成的小范围修复

- 每轮检查都会选择旧的待处理简报，并在新内容之前处理最多 5 条；旧任务按发现时间排序，同一条内容不在本轮重复处理。
- 单条分析的超时、连接中断、HTTP 408、429 和临时 5xx 错误有限重试，沿用 `retry_attempts`、`retry_minutes`。默认额外重试一次、等待 5 分钟；单条最多额外重试 3 次、每次等待最多 10 分钟。配置、余额、证书和访问验证错误不重复请求。
- `--no-retry` 同时关闭外层调度和单条处理的重试；命令行重试延迟也传递到单条处理。
- 知乎摘要生成和历史恢复共用缓存标识，已有成功缓存能够恢复错误或中断状态，保留阅读状态。

这组早期修复保留在 JSON 兼容路径中。SQLite 生产路径改为持久队列和独立工作进程，延迟重试不占用元数据调度进程；底层 AI 请求自身的有限重试仍存在。

## 一 增量抓取与首次关注边界

### 问题与目标

旧版本 B站、知乎及 RSS/RSSHub 在定时路径中最多保留最近 3 条。这个数量适合首次展示，不足以承担日常增量检查。抖音原来在第一条非置顶的已收录内容处截断，能够避免初次关注后导入旧作品，但可能跳过已加载批次中已知作品之间的缺口。

仅凭 `seen_ids` 无法判断缺口是初次关注之前的历史，还是关注后的漏收。抖音直接把第一个锚点改成最后一个锚点会破坏现有历史边界测试，因此应先建立独立的关注边界。

### 抓取协议

统一返回 `FetchResult`，包含内容列表、后续页标识、是否确认到达历史边界、是否确认读完、停止原因、可恢复错误和抓取警告。一次空列表只有在确认没有更新时才表示成功；未加载、验证失败和解析变化分别记录状态。

每个来源保存以下信息：

| 字段 | 用途 |
| --- | --- |
| `followed_at` | 关注时间，区分首次展示与后续更新 |
| `baseline_ids` | 首次发现的作品集合，首次展示仍只取 3 条 |
| `baseline_boundary` | 平台能够提供时记录稳定的作品时间或排序位置 |
| `checkpoint` | 上次完整检查的定位信息与版本 |
| `catchup_cursor` | 本轮未补齐时继续读取的位置 |
| `catchup_anchor_ids` | 补抓期间冻结的旧锚点，不随新内容入库提前推进 |
| `last_success_at` / `last_attempt_at` | 分别表示成功检查和最近尝试 |
| `scan_status` / `stop_reason` | 完整、部分、失败及停止原因 |

先把发现的内容持久化，再确认收录；只有完成整个检查范围才推进完整检查点。达到页数或时间预算时保存补抓位置并标记“部分完成”，下一轮继续补抓，同时重新检查首页，避免补抓期间漏掉新作品。

抖音在同一批次中检查所有未知 ID，以关注边界过滤旧作品，排除置顶作品作为停止锚点。允许一定的重叠扫描，周期性核对已确认范围内的缺口。发布时间不可靠、作品排序变化或游标失效时，应重新扫描受限范围并提示范围无法确认。

### 各平台实现

- **B站：** 动态流利用实际响应提供的分页标识；没有可靠分页时使用投稿列表分页回退。统一去重 BVID，限制动态和投稿回退的总请求预算。
- **知乎：** API 路径使用其分页信息；浏览器路径使用有上限的滚动采集。原创内容筛选先执行，抓取窗口再停止，避免点赞等动态挤掉真实更新。
- **RSS/RSSHub：** 读取当前 Feed 中所有条目再去重，不再先截成 3 条；优先 GUID/Atom ID，缺失时使用规范化链接。保留体积与超时上限，支持 ETag、Last-Modified 和 304。没有公开历史的 Feed 无法补齐已经从 Feed 移出的条目，应明确提示这一限制。
- **小红书：** 保留现有发现队列与冻结锚点机制，接入统一返回结构；采集详情失败不清除发现队列，列表发现与详情读取分别记账。

旧来源没有可靠关注边界时，以当前已知集合建立迁移边界，不自动导入未知旧历史；提供单独的手动补抓操作，明确范围和内容数量。不能把未知时间视为“肯定是新发布”。

### 验收

一次检查间隔产生 8 条更新时，在可读取范围内全部入库；测试置顶、批次内缺口、相同时间戳、延迟公开、重复页、删除作品和游标失效。达到预算时必须显示部分完成，后续轮次能继续到冻结锚点。首次关注前的历史不会自动变成未读更新。

## 二 统一任务队列与跨进程执行

### 执行结构

定时检查、首次关注、手动重试和重新分析都提交任务。网页请求只返回任务 ID 和状态；一个工作进程负责领任务，避免网页进程退出使后台线程消失。元数据采集与 AI 分析分别排队，长视频不阻塞其他来源发现更新。

任务以 `(platform, content_id, task_type, analysis_version)` 建立唯一约束。分析版本由模型、分析配置、内容指纹和提示词版本生成；相同版本重复提交复用现有任务，明确重新分析可创建新版本，成功前仍展示上次结果。

状态流转为：`queued → running → succeeded`，临时失败进入 `retry_wait`，永久错误或超出预算进入 `failed`，用户主动取消进入 `cancelled`。每次尝试单独保存开始时间、阶段、耗时、错误类别和结果位置。

### 占用与恢复

在同一数据库事务中领取任务，写入 owner、递增的领取代次和 lease 期限；执行中定期更新心跳。只有当前 owner 和代次可以提交进度和结果，防止旧工作进程覆盖重领任务的结果。

工作进程崩溃后，过期 lease 的任务转回待处理；成功片段和媒体缓存可复用。任务结果文件先原子发布，再在数据库中标记成功；文件成功但状态提交中断时，通过结果指纹恢复，不重复调用 AI。

外部模型服务通常不能保证幂等调用：请求已计费但本地未收到响应时仍可能产生重复费用。应保留请求 ID（服务提供时）、阶段结果和请求指纹，避免宣称完全“只执行一次”。

### 公平性与资源预算

按来源轮转，旧任务等待时间越久优先级越高；手动任务可以提高优先级，但不能长期挤压旧任务。初始建议为浏览器采集并发 1、CPU 转写并发 1、AI 请求并发 1，分别可配置；API 元数据采集可逐步尝试并发 2。

每个平台独立控制最小请求间隔和失败冷却，避免所有平台共用一个限速值。达到服务用量或本轮处理预算时暂停领取新分析任务，发现的新内容仍正常入库。

### 错误与重试

通过结构化错误类别处理重试，逐步替代字符串匹配。超时、连接中断、HTTP 408、429、5xx 使用指数退避和随机抖动；有合法 `Retry-After` 时优先遵循并设置上限。所有层级共用尝试预算，避免“片段重试 × 请求重试 × 调度重试”放大调用量。

401、402、凭证解密失败、模型配置错误和需要人工验证的任务进入待处理状态并给出具体操作。用户更新相关配置后，只恢复对应类别的任务。失败来源可以进入冷却，成功来源继续检查。旧的临时失败记录只在迁移后取得明确的次数和预算，不无限恢复重试。

### 验收

网页和调度器同时提交同一内容只产生一个活跃任务；测试进程被结束、心跳超时、旧 owner 延迟返回、磁盘写入失败和任务取消。持续产生新内容时旧任务能获得执行机会。配置错误不产生连续请求，429 不触发快速循环，服务端请求次数符合总预算。

## 三 历史保留与 SQLite 迁移

### 数据结构

建议使用标准库 SQLite，开启 WAL 和合理的 busy timeout，以短事务更新状态，避免网络请求期间持有数据库事务。JSON 继续作为导出格式。

| 表 | 主要内容与约束 |
| --- | --- |
| `sources` | 平台与来源唯一键、关注边界、抓取位置、检查状态 |
| `contents` | 平台与内容 ID 唯一键、公开元数据、发现时间、阅读状态 |
| `source_contents` | 来源与内容关系，避免多个来源收录同一内容时互相覆盖 |
| `jobs` | 任务唯一键、状态、预算、下次重试时间、owner 和 lease |
| `job_attempts` | 每次尝试的阶段、错误类别和耗时 |
| `analysis_results` | 内容版本、模型与配置指纹、结果文件路径和完整性 |
| `checks` | 每轮检查与各来源的结果、抓取数、补抓范围 |
| `schema_migrations` | 版本与迁移完成记录 |

内容查询按发现时间和 ID 稳定排序，采用游标分页；未读数量通过查询计算，不依赖只读前 1000 条的快照。对状态、下次重试时间、来源、发现时间建立查询索引。

### 保留策略

未读、待处理、重试中和需要人工处理的记录不参与普通清理。已读且完成的内容按保留时间归档，默认保留正文索引和成功简报；原始媒体、采样画面与旧模型缓存分别设置容量和过期策略。清理前排除活跃任务引用的文件，提供容量统计与预览，再执行用户选择的清理。

SQLite 生产路径已取消保存硬截断，历史分页独立于存储数量；已经被旧版本裁掉且没有完整副本的元数据无法保证自动恢复。SQLite 状态和批次内容修改已只写涉及记录；JSON 兼容层、导出及部分聚合查询仍读取全量历史。

### 迁移与回退

1. 暂停采集和任务提交，确认旧网页后台线程与调度器退出，备份现有 JSON 和成功缓存清单；记录文件哈希和条目数。
2. 在新数据库中开启事务，导入来源、去重集合、历史、阅读状态和缓存索引。非法条目保留在迁移诊断中，不静默丢弃。
3. 按平台和内容 ID 去重，优先保留成功结果与阅读时间；中断的 processing 任务转成 queued，保留此前错误记录。
4. 核对来源数、内容数、未读数、成功简报数和缓存路径，完成后写入版本标记，原子启用新存储。任一校验失败继续使用原存储。
5. 保留旧备份和迁移日志，迁移必须可重复执行而不重复插入。启用后的备份使用 SQLite backup API；不能只复制活动数据库主文件而遗漏 WAL。
6. 回退前停止新工作进程，把迁移后新增内容和阅读变更导出为兼容 JSON，再恢复旧程序；仅恢复旧备份会丢失这段新增数据，应提示并保留导出文件。

### 验收

以超过 1000 条、包含未读和未完成任务的数据迁移，逐条核对身份、阅读状态和成功结果。测试事务回滚、重复迁移、损坏 JSON、磁盘满、并发读写、正在处理文件的清理保护，以及包含迁移后新增数据的回退。

## 四 运行状态与反馈

任务面板分别显示来源最近成功时间、最近尝试、抓取是否完整、补抓位置状态，以及 queued、running、retry_wait、failed 数量。计划任务已启用只表示调度配置正常，不能作为所有来源抓取成功的结论。

新增任务状态和来源状态接口，显示具体错误类别及“重新登录”“检查 AI 接入”“重试”操作。运行日志关联检查 ID、任务 ID 和尝试次数，记录各阶段耗时；对 Cookie、API Key 和带私密参数的 URL 脱敏。只有有更新、持续失败、恢复成功或需要用户操作时通知。

元数据刷新保存内容指纹；公开正文确实变化时标记摘要可能过期，按用户设置重新分析，保留原摘要和阅读状态。该能力依赖版本化任务与结果，不在本轮小修复中自动启用。
